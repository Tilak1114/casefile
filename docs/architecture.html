Casefile · harness v2 · as built and measured

An event-driven claims team, and what it remembers

This page is the harness v2 design as built, and what its runs measured. Terms: the claim file is the whole package the team works on (88 source PDFs); a source PDF is one of the 94 numbered PDFs in the NTSB docket; a document is one original letter, report or form inside a PDF. Harness v2 models how a carrier works a construction-defect liability claim: a claim professional leads, defense counsel works the parties and contracts, a forensic engineer is retained with the lead's approval, and they coordinate through events rather than calling each other. Everything below is built unless marked planned or proposed. Roles and sequence are sourced in docs/00b-claims-team.md; the plan is docs/06-harness-v2.md.

A different, stronger model, so this compares model and harness together, from one pass per agent. The fair next test is a generic agent loop on the same Gemini model. The agents' output and the scorer are in the repository (data/cases/HWY06MH024/comparisons/claude-code-1/, scripts/score_claude_comparison.py).

Each round of changes came from loss attribution on the run before it. v2-full-1 lost daily-report entries read in one oversized call and quotes broken across hyphenated lines: readers now read long documents in page windows, report each dated log entry, and the verifier joins hyphenated words. v2-full-2 lost two events on one-page transmittals the lead chose to skip: the lead can no longer exclude documents. v2-full-3 reads everything and misses no answer-key event. The weak spot is relationships: the model links two companies, but the quote often does not show the link, so the verifier refuses it.

Why v2: what run full-1 showed

Run full-1 used v1: one examiner deciding one action per turn. Measured on the run before it stopped at turn 26 during an Atlas failover:

11 of 27turns spent on repairs instead of assigning work
421 / 1,737pages read; all correspondence read, most unread pages were bulk FHWA and MIT test data
7% vs 35%claims refused by the verifier: harness vs a single prompt on the same model
2 of 13answer-key relationships found; no absences reached

So v2 changes three things: the work is split across a team that runs in parallel, repairs become automatic, and the goal is no longer to read every page but to read what each task needs, with the rest indexed and any exclusion stated. (Later runs showed exclusions cost key events; every document is now read. See the result above.)

The team and the event log

Every interaction is an event appended to one collection in MongoDB. Each role is an independent agent that wakes when an event addressed to it arrives, works, publishes events and goes back to waiting. Code components (the dispatcher, the verifier, assembly) react to the same log.

Each team member

Every agent is specified the same way, and the harness enforces it: what wakes it, what it must wait for, what it is allowed to see and do, what it publishes, and what it may never do. The dispatcher, verifier and assembly are code and follow the rules shown above.

Stand in for the reading a person does. Started by counsel or the engineer.
Job
Read a batch of whole documents (about 40k characters; long documents in consecutive page windows) with the role's focus, reporting each dated entry of a log as its own event. Return dated events, parties, relationships, aliases and open questions, each quoted with its page.

Model

Model choice: gemini-3.8-flash for every agent, the model the single-prompt baseline and run full-1 used, so the comparison is fair. On a three-document test it refused 9% of its claims; cheaper Flash models refused 33–41%, failing mostly on relationships and aliases.

Retrieval: the records desk

Retrieval is a lookup, not a judgement, so it is deterministic code exposed as typed, read-only tools, and the agents decide what to look up. There is no separate retrieval agent. Every tool hides production labels and withheld PDFs and writes coverage automatically. Agents never get raw database queries; the MongoDB MCP server stays a tool for developers.

Readers get narrow retrieval, about two extra documents each, to resolve a reference like “see our letter of 12 October” on the spot; anything bigger goes back to the role as an open question. Counsel and the engineer get the full set. The lead gets metadata and counts only, so it never sees page text.

Keeping context from thinning up the hierarchy

Each layer can only pass up what the layer below noticed. Measured on run full-1, the 22 missed answer-key events were lost here. The dominant loss was what nobody read, not what readers dropped.

Where it was lostMissedWhat it means

Read, but no claim made1the reader-level loss: E22, Powers reporting 120 ft-lb torque above the 50–90 range

Claims are pointers, not summariesEvery claim carries its source PDF, page and exact quote; any role can open the full document at any time. What travels up is a reference, not a retelling.
Gaps are visibleCoverage records who read each page and with what focus, so the lead can see what nobody has looked at through, say, a technical lens.
Deliberate overlapKey document types (correspondence, submittals, deficiency reports) are read by both roles with their own focus. In full-1 no document was read by both; in v2-full-3, 75 of 172 were. The one-reviewer ablation measures whether the overlap earns its cost.
Roles can read for themselvesCounsel and the engineer can read a high-value document directly, not only through readers.
Loose ends travel as eventsOpen questions and unresolved references are published as events the roles must act on.
Loss attribution in every evaluationEach missed answer-key event is attributed to where it was lost: never read, read but not claimed, claimed but refused, or a different date.

How a claim moves through the team

The order follows a carrier's published guidelines for construction-defect counsel: counsel is assigned, asks the lead for prior written approval to retain an expert, reports an initial assessment, and requests further work. Roles work in parallel between these points. The request and the dispute below are illustrative of the mechanism; the events are the real catalogue.

Independent work, declared dependencies

Tasks wait for events, not for each other Every task carries waits_for: the events that must exist before it can start. The engineer's first task waits for expert.approved; counsel's status report waits for the answer to any request it raised. The dispatcher starts a task the moment its conditions are met.
Task states
Nothing lost, nothing done twice Consumers record the event ids they have handled and their change-stream resume token. After a crash every role resumes from its LangGraph checkpoint and the log, so a failover like the one that stopped run full-1 should cost nothing. (Designed and unit-tested; not yet tested by a real failover.)
Reading what the task needs Every document is indexed at ingestion (type, date, author, recipient, search). Every document is read in full by some role before the file can close (decision 30: the lead’s exclusions cost key events in v2-full-2). Absences can only be claimed over pages read in full.

Disputes, coverage and models

Disputes A role opens a dispute when another role's claim conflicts with its own: a different date for the same event, two documents that disagree, a relationship its evidence contradicts. About what a page says: the verifier rechecks deterministically and rules. About what it means: the lead convenes a roundtable; each side submits a position with citations; the lead rules, citing evidence. Both positions stay on the record. In v2-full-3 counsel and the engineer opened 8 disputes over dates; the lead ruled each, citing the quotes. How carriers settle disagreements between their own experts is unsourced, so the lead's ruling is our design choice and the UI says so.
Coverage in two levels Indexed: every document, free, from ingestion (type, date, author, recipient, pages) and search. Read in full: the pages a reader was given, logged before the model runs and removed again if the call fails. Every document is read before the file can close; the lead cannot exclude documents (decision 30). Absences can only be claimed over pages read in full and must survive a search for counter-examples.
Models google/gemini-3.8-flash via OpenRouter for every agent, the model the baseline and full-1 used, so the comparison is fair. Each call also records the provider’s summary of the model’s reasoning, shown on the Trajectory screen. Three-document test: 3.8-flash refused 9% of its claims; 2.5-flash 33%, 3.1-flash-lite 37%, 2.5-flash-lite 41%. Kept for a later cost pass.

Decisions since approval

  1. The lead retains the engineer on its own initiative too (in smoke-2 counsel never asked).
  2. Readers are batched by characters and read long documents in windows; log entries are reported one by one.
  3. The verifier joins words across hyphenated line breaks; names match across formatting and through verified aliases.
  4. No exclusions: every document is read before the file closes (decision 30).
  5. Every model call records its decision and the provider’s reasoning summary.
  6. 16 model calls at once; rate limits back off; a failed batch releases its pages.
  7. The answer key’s evidence audited against all 88 input files, independently of any run.
