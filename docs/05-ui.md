# Step 6: the UI and design system

Status: plan for approval, 2026-09-26.

The demo is a finished run, not a live agent. The UI's job is to show the investigation the harness
produced and how the harness produced it: the chain of events on the project, the evidence behind every
line, how the harness is set up, and how it managed memory. It must look like software a claims team
would use, not a generated dashboard.

## Who uses it

The liability-side claims examiner and defense counsel (Step 0). They read evidence, check quotes
against the page, and hand a chronology, a party map and an exhibit list to experts and counsel.

## Screens

1. **Board** (the main screen): an investigation board on a pannable, zoomable canvas.
   - Time runs left to right (1997 to 2007); one horizontal lane per party from the party map.
   - Each verified event is a card on its lane at its date; documents that answer each other (a reply
     quoting a letter's reference number) are joined by lines; relationships between parties are drawn
     between lanes.
   - Clicking a card opens the **evidence panel**: the quote highlighted on the page image, the checks
     it passed (quote on page, date, names), the document's metadata, and every other claim citing the
     same page.
   - Filters: role, party, date range, core chain only.
2. **Chronology**: a dense, sortable table of verified events with quote and page, the deliverable an
   examiner hands over. Duplicates merged; each row opens the evidence panel.
3. **Parties**: the project hierarchy (owner and authorities, management consultant, designers,
   contractor, suppliers, testing agencies) with every link cited; names merged only on formatting or a
   quoted alias, and each alias shown with its quote.
4. **Harness**: how it is set up, drawn from the code: the examiner and the two reviewer roles with their
   tools and context, readers and their cap, the guards, the verifier's rules. Below it, the run replay:
   each turn's decision, readers started, tokens, and whether an action was rejected and why.
5. **Memory**: what the run knew and when. A coverage map of all 173 documents (read, by which role,
   unread, withheld), verified findings and refusals per turn, the examiner's context size per turn (it
   stays bounded however much is read), repairs, and negatives with the searches that tested them.
6. **Evaluation**: the run against the single-prompt baseline, dev and held-out separately, and the
   answer key review (every key event: found or missed, with its NTSB page and the run's evidence).

Every screen labels the case as a real public NTSB docket and states that Casefile quotes documents and
never assigns fault.

## Data

- `casefile export RUN_ID` writes the run from Atlas to static JSON (typed with the same Pydantic models,
  with generated TypeScript types) plus page images for every cited page, rendered from the PDFs in
  GridFS.
- The web app reads only that export, so the deployed demo needs no database and cannot break.

## Stack

- Next.js (App Router) with TypeScript, static export, deployed on Vercel.
- Canvas: React Flow (`@xyflow/react`) for the board, with custom nodes and edges.
- Primitives: Radix UI for accessible behaviour (dialogs, tabs, popovers, tooltips); our own styling.
- Styling: CSS variables for design tokens and CSS modules; no component kit look.
- Charts: hand-built SVG for the few charts (coverage, context size, findings per turn).

## Design system

- **Tokens**: colour roles (surface, ink, line, accent, and semantic: verified, refused, pending,
  interpretation, withheld), a type scale, a 4px spacing grid, radii, elevation, motion, and density.
- **Components**: case header, evidence card, quote with highlight, page viewer, status pill, check
  list, lane, event node, thread edge, data table, coverage cell, turn row, metric, empty and error
  states.
- **Both themes** from the same tokens; keyboard navigation and visible focus throughout.
- Two directions are proposed in the mockups; one is chosen before building.

## Build order

1. Export command and TypeScript types.
2. Tokens and base components, on a component page.
3. Board with the evidence panel.
4. Chronology and Parties.
5. Harness and Memory.
6. Evaluation and answer key review.
7. Deploy.
